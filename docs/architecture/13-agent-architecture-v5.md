# 文渊 · Agent 分析架构 v5.1（模型能力优先 · 双 tier 身份解析）

> 本文档是分析域的**当前权威架构**，取代 v4（`12-agent-architecture-full.md`）与 00-11 中所有 Tool-Use Loop 相关描述。
> 核心转向：**模型只做它擅长的提取，系统只做模型永远不会的验收。**
>
> 版本：2026-08-07 · v5.2（v5 经四轮评审收敛：双 tier 身份解析 + 身份判定原语 + 分布式冲突扫描 + 登记表派生视图 + 预算修正；skill 装载重构：AI 动态选 skill + 关系码契约入 skill + 功能点模型）

## 第一部分 · 设计哲学

### 1.1 为什么抛弃 v4：从"补模型缺陷"到"发挥模型能力"

v4 架构（Agent 工具循环 + 跨章记忆 + 自修复闭环）的每个组件，本质上都在补一个"模型自己做不到"的假设：

| v4 组件 | 补的缺口 | 2026 现状 |
|---|---|---|
| Agent 工具循环（lookup/search/verify/load_skill） | "模型记不住全书，得按需检索" | 1M 上下文 + 强模型直接读全章 + 注入上下文，已不需要 |
| 跨章记忆 chapter_memories | "模型跨章指代会丢" | 全书身份在 Pass0 双 tier 判出**草稿登记表**，记忆管线整体消失 |
| ValidationAgent 自修复闭环 | "提取会错，得自己纠" | **结构性错误**——让写答案的模型给自己的作业打分，已被业界否证 |
| 复杂 systemPrompt + 指令 + few-shot | "模型不知道怎么做" | 冗余指令在当前模型上会**缩小搜索空间**，是负资产 |

**教训**：`harness 里每一个组件都编码了一个关于"模型自己做不到什么"的假设；随着模型变强，这些假设会过期。` 凡是为补模型能力缺口而写的，都删。

### 1.2 哪些永不内化（必须写死在系统侧）

| 层 | 内容 | 为何永不内化 |
|---|---|---|
| L3 · 验收标准 | goldset、证据锚定判据、name authority 规范、merge 授权边界 | 模型拿不到"什么算做对了"；责任不可转移给模型 |
| L2 · 数据契约 | facts 唯一写入口、关系归一化、别名安全级别、Union-Find 护栏、关系码契约闭集（skill frontmatter + 任务快照） | 是系统不变量，靠代码/DB 强制，不靠 prompt 说服 |
| 独立复核 | 跨模型独立校验、人审例外队列 | 自评结构性偏差不随模型变强消失 |

### 1.3 一句话架构

> **确定性扫描打底 → 全书身份解析（双 tier：全局一遍草稿 + 原语兜底）→ 分片事实提取（单轮）→ 确定性护栏过滤 → 确定性聚合 → 例外优先审核 + 评测门禁。**
> 没有 agent 循环、没有跨章记忆、没有自修复闭环。模型输出即证据，系统只验收。

## 第二部分 · 分层与管线

### 2.1 分层总览

```
┌───────────────────────────────────────────────────────────────┐
│ 验收层（工具化判据，代码而非 prompt —— L2/L3）                   │
│  证据锚定 · 关系码契约闭集校验（skill 契约） · 泛称安全级别        │
│  · name authority · 幻觉过滤 · merge 人审门禁                    │
│  · 分布式冲突扫描 · goldset 评测门禁 · 定向跨模型复核              │
├───────────────────────────────────────────────────────────────┤
│ 提取层（模型自由发挥，prompt 极简）                              │
│  Tier1 身份解析（全书一遍）· Tier2 原语兜底 · 分片事实提取（单轮） │
│  结构化输出走 JSON Schema（动态生成，接口设计，不给示例）          │
├───────────────────────────────────────────────────────────────┤
│ 上下文层（渐进式披露）                                          │
│  skill 元数据常驻(~100 token) · 相关 skill 正文按 AI 动态选择注入  │
│  分片提取注入"登记表 + 全书摘要" · Tier2 注入"窗口 + 登记表 + 摘要" │
├───────────────────────────────────────────────────────────────┤
│ 数据层（权威链）                                                │
│  facts ─► relationships（物化聚合）─► Neo4j（惰性同步）           │
└───────────────────────────────────────────────────────────────┘
```

### 2.2 管线 Pass0-5

```
Pass0 全书身份解析（0-15%）—— 双 tier，见 2.3 详述
  Tier1 全书一遍草稿登记表（全局整合，1-2 次调用）
  Tier2 身份判定原语兜底（残余候选：冲突/低置信/漏网/跨卷/风险类）
  ─ 产出"身份登记表"，替代 v4 的 Pass2 全局消歧与跨章记忆
       │
       ▼
Pass1 分片事实提取（15-75%）
  输入：分片正文（5-8 章/片）+ 身份登记表 + 全书 1-2K 摘要 + 相关 skill
  输出：该片 facts + mentions + 新发现实体（交回登记表）
  ─ 身份已全局判完，片内提取是"映射到登记实体 + 提取关系/事件"
  ─ 单轮调用，无工具循环；超长章分段 + 合并（AI-Reader-V2 模式）
  ─ 新发现实体 → reconcile 走 Tier2 原语补判，不进人审（时序见 2.3：早于 Pass3 聚合与 Pass4 自动接受）
       │
       ▼
Pass2 确定性护栏（零 LLM）
  证据锚定：事实里出现的名字必须在本章正文可证（幻觉过滤）
  关系码校验：所选 skill 契约 relationshipCodes 闭集驱动（schema 动态枚举 + 落库双检）
  泛称过滤：安全级别（safety level）判据，非穷举名单
  ─ 落库 facts(DRAFT) + mentions + aliases
       │
       ▼
Pass3 确定性聚合 + 权威（零 LLM）
  alias resolver（Union-Find 合并别名，泛称不参与桥接）
  name authority（canonical 名选择 = 唯一事实来源）
  分布式冲突扫描（见 2.3，按章分布检测误归属）
  refreshRelationshipsForBook（幂等重建 relationships）
  Neo4j 惰性全量重同步
  ─ 生成 merge_suggestions（PENDING 人审）
       │
       ▼
Pass4 例外优先审核（15-90%）
  自动接受栈（见第七部分，强置信 = 证据锚定 + 提及数 + 登记表 HIGH
                + 分布式扫描干净 + 确定性校验全过）
  人审队列：仅异常（跨片冲突 / 低置信新实体 / TITLE_ONLY 泛称 /
                merge-split 建议 / 关系级幻觉定向抽样）
  棘轮校准：抽样回查自动接受准确率 → 达标放宽、不达标收紧
  ─ MERGE/SPLIT 一律人审（L3 责任边界）；非破坏修复才允许自动
       │
       ▼
Pass5 评测门禁（90-100%）
  goldset 跨段取样 + 冷门书对照 → eval gate（entityF1 / relationF1）
  Pass0 A/B 校准表选路径（离线，全书一遍 vs 分卷）
  棘轮法：只在评测暴露真实失败后，才针对性加确定性约束
  Neo4j 同步 · 任务终态落库
```

**任何 facts 变更（提取 / 审核 / 合并）后调用 `refreshRelationshipsForBook`** ——facts 是唯一写入口，relationships / Neo4j 均为派生。

### 2.3 Pass0 双 tier 详解（承重墙构造）

```
Tier1 全书一遍草稿登记表 —— 全局整合层（1-2 次调用，~300K）
  输入: 全书正文 + 确定性预扫描候选（统计召回兜底）
  输出: 草稿登记表 { canonical名 / 别名 / 类型 / 证据锚点 / 活跃章区 }
  价值: 跨候选全局交叉引用——"范老爷(ch2) ↔ 范进(ch7)"需同一遍看到两端
  前置门禁: Pass0 A/B 对照（全书一遍 vs 分卷）达标才走单遍；
            不达标 → 分卷 Tier1（一等路径，见 3.2）
  输出过大 → 按"人物/地点/组织"拆 2-3 次调用，各带全书，结果确定性合并

Tier2 身份判定原语兜底 —— 局部窗口 + 全局登记表（残余 20-40%，~200-400K）
  跑: 冲突标记 / 低置信 / 漏网高频(reconcile) / 跨卷边界 / 风险集中类
  每候选: 分层采样窗口(≤15, 按章取样) + 当前登记表 + 全书摘要 → 单次判定
  回写: HIGH → 登记表 · ambiguous → 人审+跨模型 · newEntity → MEDIUM
  边界: 原语是局部组件，永远替代不了 Tier1 的全局整合；
        只做安全网，不做主力

身份判定原语 IdentityResolutionPrimitive（HIGH 组合规则，写死）
  LLM 判定 resolved（带证据锚点）
  ∧ 提及数 ≥ 2
  ∧ 分布式冲突扫描干净（活跃章区不指向他实体）
  ∧ 采样窗口语义一致
  → 四者全过才 HIGH；否则降级 / 人审 / 跨模型
  原则: 置信参与，绝不独裁（否决 v4"D3 confidence=1.0 自动合并"的教训）

分布式冲突扫描（按章分布，非邻近 —— 防误报工厂）
  别名活跃章区由登记表 mentions 分布确定（确定性数据）
  只与实体 Y 活跃章区重合、从不与 X 重合 → 重归属 Y
  与 X、Y 均重合 → 正常同场共现，不标记
  ─ 禁止用"窗口重叠"判冲突（范老爷/范进同场共现是常态，会海量误报）
  同一代码路径跑两次: Tier2 候选级（残余集）· Pass3 全量终扫（捕跨候选交互——
  候选集在 Tier2 时还不完整，跨候选误归属只能全量扫描时发现）

reconcile（漏网高频，复用原语）
  时序: 位于 Pass1 与 Pass3 之间（必需步骤）——回写登记表必须先于 Pass3 聚合
        （分组依赖登记表）与 Pass4 自动接受（判定读登记表 HIGH），否则自动接受栈失效
  触发: DB 扫"提及数 ≥ N 但不在登记表"的表面形式（确定性穷举，漏不了）
  判定: 原语（同模型二次看）
  边界: 只补覆盖缺失【补得上】；系统误判（同一偏差二次犯）【补不上】
        → 后者靠跨模型/人审
```

## 第三部分 · 上下文策略

### 3.1 1M 上下文是架构级变量

儒林外史全文 ~33万字 ≈ **200-300K token**，整本书装得进 1M 上下文。这消灭了 v4 最大的承重墙（跨章记忆 / 全局消歧），身份解析提前到 Pass0 双 tier 判出草稿登记表。

**两个隐藏约束必须正视：**
1. **输出长度才是瓶颈**：一次吐全书全部事实 ≈ 50-100K 输出，超模型输出上限。→ **输入可以整本书，输出必须分片**。
2. **成本**：每读一次全书 = 300K 输入。→ 依赖 DeepSeek 前缀缓存（重复读同一本书共享前缀 ≈ 0.1x）；分片调用上下文小，本身便宜。

**1M 解决的是 coverage，不是 integration**：标称窗口大 ≠ 长程整合强。跨章指代（范老爷→范进）是主动检索 + 全局比对，比 needle-in-haystack 难，Lost in the Middle 真实存在。这正是 Tier1 要前置 A/B 门禁、Tier2 要兜底的原因——单遍是"待验证的赌注"，不是既定事实。

### 3.2 上下文与"书大小"的相对关系（架构的稳健性）

架构依赖的是**"书能装下"这个阈值**，不是 1M 这个具体数字：

| 上下文 vs 书 | Tier1 身份解析 | Pass1 事实提取 | 架构是否变化 |
|---|---|---|---|
| 128K < 书 | **分卷 Tier1（一等路径）** | 分片 | 分卷是一等路径，骨架不变 |
| 1M ≥ 书（目标） | 全书一遍（1-3 次调用） | 分片 | 最优路径 |
| 10M ≫ 书 | 全书一遍（轻松） | 可升级"全书按 factType 多遍" | 质量上限更高，骨架不变 |

**分卷 Tier1（一等路径，旗舰书是常态）**：

- 相邻卷重叠衔接（卷 i 带卷 i+1 开头几章，跨卷人物有上下文衔接）
- 卷级登记表合并 = 用身份判定原语处理跨卷边界候选（重叠章成员身份对齐两卷登记表）
- 仍是"几次整卷读取 + 确定性合并"，比 v4 的 agent 循环简单一个量级

**越大越要留验证层**：attention 稀释与"自信的错误"不随上下文变大而消失。上下文增长改变"每次决策能看多少"，不改变"每个决策都要验收"。

## 第四部分 · Prompt 设计（减法原则）

模型现在很强，prompt 只写**模型拿不到的东西**：

**写（保留）**：
- 目标："提取本章实体与事实" / "输出全书实体登记表"
- 输出契约：JSON Schema（**运行时动态生成**：factType 枚举、关系码取自所选 skill 契约快照、evidence 必填、字段约束）
- 成功判据："每条事实必须有原文证据；实体名必须在正文出现"
- 可用上下文：章正文 + 身份登记表 + 全书摘要 + 相关 skill
- 约束：只提取本章可见事实，不臆测前文未出现的信息

**删（不写）**：
- ❌ 分步流程指引（"先找实体再找关系"）—— 路径留给模型
- ❌ CRITICAL / MUST / 强调语 —— 过度触发
- ❌ 负面指令（"不要提取泛称"）—— 点名负面项效果更差
- ❌ 工具用法 / 调用规则 —— 没有工具了
- ❌ few-shot 示例 —— **示例会成为约束**，schema 就是接口
- ❌ 自由 JSON + repairJson —— 结构化输出走 function calling / response_format

**systemPrompt 期望规模 ≤ 300-500 token**（目标 + 判据 + 约束），比 v4 的"systemPrompt(skill 组装) + 指令 + 工具说明"小一个量级。

## 第五部分 · Skill 系统（只承载 L3 知识）

按"复述默认行为的 skill 零价值"判据，重定义 skill 边界：

| 保留（L3：模型从正文/训练拿不到） | 删除（模型默认就会 / 可下沉为代码） |
|---|---|
| 书型特有知识：科举制（座师/同年/门生）、官场规则 | "如何提取实体/关系"的过程指令 |
| 历史人物事实（真名溯源：周进→周学道） | 通用中文命名常识（姓氏/名字模式） |
| 书型级别名模式（明清官场称谓规则） | 泛化的"古典文学常识"复述 |
| 关系类型契约（relationshipCodes 闭集，schema/guardrail/图谱取码源） | 字典式穷举规则（代码不维护码表，码进 skill frontmatter） |

**装载方式（v5：AI 动态选择，每次任务现选）**：解析前由 `selectSkillsForJob` 按"书 + skill 目录"动态选 skill——书上下文（书名/作者/朝代/简介 + 章节正文：全文 ≤ 阈值全量注入，超长抽样首/中/末各 ~2K 字）+ frontmatter-only 目录 `{slug, name, description, category}`（不读正文）→ 一次 SKILL_SELECTOR 廉价模型调用 → zod 校验 `skillSlugs ⊆ 目录`（目录外/未启用的 slug 丢弃告警）→ 装载集合 = `scope=GLOBAL ∪ 选中` → 结果快照进 `analysis_jobs.skillsSnapshot` / `relationshipTypesSnapshot`。任务内各阶段从任务快照装载，任务间互不干扰；**不做书级持久化**（同书多次解析每次现选）。skill 元数据（名字 + 描述 ~100 token）用于选择器目录与管理 UI 展示。

**启停（`Skill.isEnabled`）**：每个 skill 独立开关（非总闸）；`false` = 该 skill 全局不可用（目录不可见 / AI 不可选 / 不装载）。内容源 = `scripts/skills/*.md`（frontmatter 契约 + 正文）+ seed，管理端只读展示契约 + 启停开关，不提供富文本编辑。

**关系码契约（v5：relationship_types 表已删）**：关系码闭集进 relationship-type skill frontmatter `relationshipCodes: [{code, direction, category, aliases}]`（seed：`classical-relationship-types.md`）；运行时 schema/guardrail/图谱取码 = 所选 skill 契约并集（去重按 code，先到先得）+ 任务快照 `relationshipTypesSnapshot`。虚指代词名单同样外置为 GLOBAL skill 契约（`chinese-deictic-junk.md` 的 `deicticJunk`），guardrails 从装载上下文读契约，代码只留空名单兜底。

**SkillGenerator（规划中，未接线）**：生成全自动候选 + 人工确认启用的模块（`src/server/modules/skills/skillGenerator.ts`）已实现但**未接入任何运行时路径**（无 admin API / 管线调用）；Skill 模型保留 `generatedFromJobId/generatedFromBookId` 溯源字段与 `SKILL_GENERATION` runType 枚举。启用须人确认（L3 信息必须人盖章）。

## 第六部分 · 数据模型调整

基于现有 schema（已迁移的新库；skill 装载重构后：删 `book_types`/`book_type_skills`/`relationship_types`/`model_strategy_configs`/`text_chunks`/`fact_evidences` 6 表，新增 `feature_models` 表），**运行域按"无工具循环"简化**：

| 表 | 处置 | 理由 |
|---|---|---|
| `facts` / `entities` / `aliases` / `mentions` / `relationships` | **保留** | 权威链不变（`fact_evidences` 已删，证据锚定只写 `Fact.evidence`） |
| `skills` / `skill_versions` | **保留** | L3 知识承载；`Skill` 增 `isEnabled` 独立启停开关（v5）；`book_type_skills` 已删（书型间接层） |
| `relationship_types` | **已删** | 关系码权威表取消，契约入 skill frontmatter（`relationshipCodes` 闭集）；运行时取码 = 所选 skill 契约并集 + `analysis_jobs.relationshipTypesSnapshot` 任务快照 |
| `analysis_jobs` | **保留**，简化 scope | 任务生命周期；`skillsSnapshot` / `relationshipTypesSnapshot` 由 `selectSkillsForJob` 在任务启动时写入 |
| `agent_runs` | **保留**，runType 补全 | runType = PRESCAN \| IDENTITY \| EXTRACTION \| RECONCILE \| VALIDATION \| CROSS_VALIDATION \| SKILL_GENERATION（QaAgent 用户问答不落 agent_runs） |
| `agent_steps` | **删除**（或降级为 segment 成本记录） | 无工具调用，`kind=TOOL_CALL` 等枚举作废 |
| `agent_write_audits` | **保留但简化** | 只记提取落库写审计（evidence 校验通过记录） |
| `chapter_memories` | **不建** | 身份登记表就是记忆；无跨章记忆管线 |
| `validation_reports` / `merge_suggestions` | **保留** | 只检测不修复；merge 人审 |
| `text_chunks` / pgvector | **已删** | RAG 是 v4；v5 无检索问答路径 |
| `feature_models` | **新增** | 功能点模型全局映射（featureKey → modelId；SKILL_SELECTOR / PIPELINE_MAIN / REVIEW），AiCallExecutor 按 featureKey 解析，未配置回退系统默认模型 |
| `facts.status` / `recordSource` | **微调** | 加 `AUTO_VERIFIED` 来源，区分机器自动接受 vs 人工确认 |

**进度推导**：`Book.parseProgress/parseStage` 列已删，解析进度由 `getBookStatus` 从最新 `AnalysisJob` 状态 + `analysis_phase_logs` 推导（前端读 API 字段名不变）；`Chapter.parseStatus` 保留（pipeline 写入、前端面板消费）。

**身份登记表（registry）物理形态 —— 派生视图，无新表**：物理载体 = `entities`（canonical 全局）+ `aliases`（书级，entityId+bookId，`status/confidence/recordSource` 骑身份置信）+ `mentions`（证据 / 活跃章区）+ `entity_profiles`（书级档案）。四路回写（Tier1 / Tier2 / reconcile / 跨模型复核）统一走 `identityService` 单一写路径（写 entities/aliases/mentions + `agent_write_audits` 审计）；登记表只是这本书身份状态的物化查询——与"facts 唯一写入口、relationships 派生"同一哲学。HIGH/MEDIUM/LOW 为**派生分类**（aliases.status + confidence + 提及数 + 活跃章区重叠推导），不落新表写。本书级别名映射（范老爷→范进）存于 aliases，**不属 skill**。

## 第七部分 · 人工审核：例外优先（Review-by-Exception）

**原则：默认接受 + 人工只看异常。** 审核量应与"真实歧义数量"成正比，而非与"总事实量"成正比。

### 7.1 自动接受栈（强置信定义）

一条事实自动落 VERIFIED，需要**可验证的客观信号**，不靠模型自报置信度：

1. **证据锚定通过**：事实里所有名字都能在本章正文确定性找到（幻觉过滤器）
2. **实体在身份登记表 HIGH**：不在登记表或 LOW → 不进自动接受
3. **提及数 ≥ 2**：单次提及且证据单薄的事实不自动接受（markOrphan 降级）
4. **分布式冲突扫描干净**：涉及实体无误归属冲突
5. **确定性校验全过**：关系码在所选 skill 契约 relationshipCodes 闭集（任务快照）、方向正确、不与已有事实冲突

**跨片/跨章一致 = 加分项，不用于免审**：多片同模型同 prompt 同登记表，错误高度相关——"≥2 片一致"只能证明不是孤例，不能证明是对的。独立信号来自跨模型，不来自跨片。

### 7.2 人工审核队列（只留这些）

| 进人审队列 | 为什么 |
|---|---|
| 跨片冲突（同一关系被提取为不同类型） | 真歧义，需要人判断 |
| 新实体且低置信 / TITLE_ONLY 泛称无法溯源 | 身份不确定 |
| **merge / split 建议** | 高危操作，仍保留人审（L3，不能省） |
| 关系级幻觉定向抽样 | 证据锚定覆盖不到的残留风险（见 7.4） |
| 自动接受校准抽样（棘轮回查） | 校准自动接受质量 |

### 7.3 棘轮校准（让人工压力随系统变好而下降）

每批自动接受后抽样人工回查，度量**自动接受准确率**：

- 准确率 > 阈值 → 放宽自动接受（提高置信下限 / 减少抽样）
- 准确率 < 阈值 → 收紧（把更多类型放进人审队列）

人工量不是恒定值，而是随系统被验证可靠而递减（back pressure：自主度上限 = 能廉价可靠验证的程度）。

### 7.4 关系级幻觉残留（显式标注，不假装不存在）

证据锚定只证"名字在正文"，**不证"关系/事件为真"**。两类幻觉能穿过锚定：

- 真实实体 + 捏造关系：A、B 都在正文，但"父子"是编的 → 锚定全过
- 真实实体 + 捏造传记事件：范进出现过，但"范进某年卒"是编的 → 锚定全过

兜底（不是消除）：**定向抽样**——双方实体真实但证据单薄的关系边、新实体率高的分片 → 进跨模型复核 / 人审。比均匀抽 5% 有效一个量级。此残留风险无法完全消除（AI-Reader-V2 同样兜不住），必须显式承认。

## 第八部分 · 评测与质量门禁（先建裁判）

AI-Reader-V2 最值得学的是把质量当工程做（498 pytest + golden standard 回归 + benchmark + IAA + ablation）：

1. **goldset 跨段取样**：首段（王冕，人物稀疏）+ **中段科举硬章节（范进/周进/张静斋，歧义密度最高）** + 尾段，共 4-6 章——首段 goldset 是整本书质量的差代理，必须跨段。
2. **冷门书对照**：加一本模型预训练大概率没吃过的同类书（2-3 章）——儒林外史（范进中举是教材内容）在模型记忆里，用它验证 Pass0 测的是记忆不是长上下文整合机制。
3. **Pass0 A/B 校准（离线，非每书两遍）**：对 goldset / 冷门书跑一次"全书一遍 vs 分卷"，产出"模型 × 书大小分档 → 默认路径"校准表；生产任务查表选路径（单遍 / 分卷），仅在模型升级或某书异常时重跑——避免每次分析都跑对照使 Pass0 成本翻倍。
4. **eval gate**：`pnpm eval:gate` 门禁（entityF1≥0.74 / relationF1≥0.68），PR 前必须过。
5. **棘轮法**：只有评测暴露真实失败，才加确定性约束。**禁止先写校验规则防猜测的失败**——旧系统 6 类 337+ 垃圾 profile 正是"规则写在失败观察之前"的产物。
6. **独立复核定向**（非均匀抽样）：同名/近名簇、多候选 TITLE_ONLY、跨卷边界实体、关系级幻觉定向样本 → 用身份判定原语**换模型**复核（跨模型验证价值不衰减）。

## 第九部分 · Token 成本账本

儒林外史 56 章，估算（含消除多轮重发，诚实标注 Tier2 成本）：

| 阶段 | v4（工具循环） | v5.1（双 tier + 单轮提取） |
|---|---|---|
| 预扫描 + Tier1 身份解析 | ~20K + 全局消歧 ~50K | **~320K**（全书一遍 + 预扫描候选，缓存可摊薄） |
| Tier2 原语兜底（残余 20-40%） | 0（无此环节） | **~200-400K**（分层采样 ≤15 窗口/候选） |
| 分片事实提取 | ~750K（多轮有穿预算风险） | **~400K**（10-12 片 × 30K 上下文，单轮无重发） |
| 聚合 / 护栏 | 0 | **0（确定性）** |
| 校验 | ~150K（模型自修复） | **~10K（确定性）+ 定向跨模型抽样** |
| **合计** | **~0.92M**（不稳定） | **~0.93-1.13M**（稳定、可并行、可缓存） |

**诚实说明**：v5.1 的绝对数不降反微升（双 tier 的 Tier2 不是免费的），但**稳定性 > 绝对值**；且 v5 的真卖点不是"更便宜"，而是**实现简单一个量级**（无 agent 循环、确定性代码可测试、无记忆管线）+ **预算即上界**：

- v4 的 0.92M 建立在"平均 1.2-2 轮"假设上，模型一漂移就穿预算
- v5.1 是**结构性单轮**，预算就是上界，不存在穿的可能
- 身份解析吃满上下文是**一次性**开销；分片调用上下文小且相互独立 → 可高并发，wall-clock 更快
- 分层采样（≤15 窗口/候选）把 Tier2 压到下限，信号损失可控
- 每次任务启动的 **SKILL_SELECTOR 动态选 skill** 为独立一次廉价调用（书上下文 + 目录，~2-4K token），全量装载技能进提取 prompt，不再按书型预注入

## 第十部分 · 扩展性 / 风险 / 与参考项目取舍

### 实现复杂度（v5 的真卖点）

实现面比 v4 小一个量级：无 agent 循环、无工具 schema、无治理层 hook、无记忆管线——管线 = 几次单轮调用 + 确定性后处理 + 审核界面，全部可单测可回归。**这是 v5 相对 v4 的真正优势，成本只是持平。**

### 扩展性

- 新书型 → 新增 skill（数据）+ 关系码契约（**编辑 skill frontmatter 的 `relationshipCodes`**），无代码改动
- 新事实类型 → JSON Schema 扩展 + 聚合映射
- 新模型 → 配置 + 上下文预算自动缩放（借鉴 AI-Reader-V2 `compute_budget`，按上下文窗口插值）
- 新质量约束 → 先在 goldset 验证失败，再写确定性校验器

### 风险（诚实标注）

1. **Tier1 单遍整合质量未实测** —— AI-Reader-V2 证明的是"逐章 + 聚合消解"，**没有**证明"单次前向推理完成全书跨章指代消解"。这是最大不确定，只能靠 Pass0 A/B 前置门禁 + 跨段 goldset 回答。回退路径：分卷 Tier1（一等路径），**不重建工具循环**。
2. **预训练混淆** —— 儒林外史在模型记忆里，Pass0 表现可能高估。冷门书对照组是唯一解药。
3. **Tier2 残余规模** —— 20-40% 是估算未实测；若残余比例过高，成本上升，且说明 Tier1 质量不足（门禁信号）。
4. **关系级幻觉残留** —— 无法消除，靠定向抽样兜底（7.4）。
5. **前缀缓存依赖** —— 全书多遍调用降本依赖 provider 缓存；架构不绑定（分卷路径不依赖缓存）。
6. **reconcile 边界** —— 同模型二次看，只补覆盖不补系统误判；实现方不得过度信任（2.3）。

### 与 AI-Reader-V2 的取舍

**借鉴**：预扫描、单轮提取、上下文注入、name authority、关系归一化、goldset 评测、token 预算缩放、错误类型化重试、L1/L2/L3 变更分级。

**不借鉴**：2000 行 FactValidator 穷举规则（大部分会被强模型内化，只留"判据级"护栏）；它没有 skill 系统（我们用 skill 承载它散落在代码里的领域知识，管理性更好）。
